# Объединение жизненного цикла расписания

## Цель

Сохранить существующий рабочий процесс создания расписания из нагрузки и утверждённый дизайн
`front_v`, объединив создание и визуализацию вокруг одного формата результата.

Две точки входа:

- `/make-timetable` — рабочее место для загрузки/редактирования учебной нагрузки, запуска генерации,
  просмотра прогресса и сохранённых вариантов.
- `/vizualize-timetable` — загрузка Excel или JSON расписания.

Оба пути должны передавать итоговое расписание общему визуализатору и поддерживать выгрузку
результата. Для обмена используется уже принимаемый backend формат TTX/1 (JSON Lines).

## Состояние текущего checkout

- Рабочее место планирования (`SchedulerPage`) и редактор/импорт JSON учебной нагрузки подключены
  к backend; прежняя функциональность генерации сохранена.
- Генерация работает через `POST /api/schedule-jobs`, опрос `GET /api/schedule-jobs/{id}` и чтение
  сохранённых вариантов через `/api/schedules`. `GET /api/schedules/{id}` возвращает результат.
- `/vizualize-timetable` использует визуализатор и дизайн `front_v`; `/review` оставлен
  совместимым адресом. `/api/review` принимает Excel Тандема и TTX/1.
- Редактор учебных данных поддерживает импорт и скачивание JSON-нагрузки. Сохранённое расписание
  можно скачать в TTX/1 или XLSX в формате студенческого расписания (отдельный лист на каждую
  группу, пары и недели I/II по строкам), либо открыть через тот же маршрут визуализации.
- В рабочем месте остаётся таблица для выбора сохранённого варианта; переход в основной
  визуализатор доступен отдельным действием.

## Этапы

### 0. Сверка существующего поведения

- Зафиксировать, какие формы, API и страницы уже используются.
- Не менять алгоритм/форму генерации при интеграции клиента.
- Проверить существующий поток генерации и не заменять его другим.

**Готово, когда:** существующий рабочий поток создания подключён без регрессий.

### 1. Объединение клиентских точек входа и дизайна

- Перенести утверждённый визуализатор и дизайн из `front_v` в `frontend`.
- Добавить `/make-timetable` и `/vizualize-timetable`.
- Оставить один компонент просмотра итогового расписания; старую точку проверки сохранить как
  совместимый адрес.
- Принимать Excel и TTX/JSON Lines на входе визуализации.
- Подключить `/make-timetable` к существующему рабочему месту планирования и сохранить прямые
  маршруты визуализации и генерации.

**Готово, когда:** генерация и импорт файла доступны из одного `frontend`, без потери имеющихся
сценариев.

### 2. Единый формат и экспорт результата

- Нормализовать сохранённый результат генератора в TTX/1.
- Добавить скачивание расписания и открытие его в общем визуализаторе.
- Не терять источник, временную сетку, группы, преподавателей, аудитории и занятия.
- Проверить полный round-trip с `/api/review`.

**Готово, когда:** сгенерированный результат открывается через тот же визуализатор, что и Excel.

### 3. Личный кабинет и нагрузка

- Показать сохранённые результаты в авторизованной области.
- Скачивание JSON нагрузки уже есть в редакторе; проверить формат и доступность из кабинета.
- Добавить Excel-экспорт расписания в формате студенческого файла, сохранив TTX/1 как основной
  машинный формат.
- Проверить структуру выгрузки тестами: заголовки группы, сетку пар, недели I/II и повторное
  открытие XLSX.

**Готово, когда:** JSON-нагрузка и расписание скачиваются из рабочего места, а XLSX открывается и
соответствует студенческой табличной раскладке.

### 4. Интеграционная проверка и документация

- Проверить маршруты, импорт, отображение, экспорт и повторный импорт.
- Запустить frontend/backend тесты и сборки.
- Обновить документацию по пользовательскому потоку и форматам.

## Принципы интеграции

- Не создавать второй генератор и не подменять существующее поведение формы нагрузки.
- Повторно использовать один визуализатор и один формат расписания на обоих входах.
- Явно показывать ошибки импорта/экспорта; не скрывать частично обработанные файлы.
- JSON — основной формат обмена; Excel — дополнительный формат для пользователя.
